Walkability Audit System.

See Live App →    GitHub →

Context.

Safe Routes to School (SRTS) is a program within the City of Pittsburgh's Department of Mobility and Infrastructure (DOMI), focused on creating safer walking and biking environments for Pittsburgh Public School students. The entire program is managed by a single coordinator, Harriet Jackson, who oversees walkability audits, school partnerships, and coordination with city planners, traffic engineers, and PPS transportation staff — all through a predominantly paper-based workflow.

Over a semester-long consulting engagement (Jan–Apr 2026), I worked with a team of two other CMU Information Systems students to design and build a two-part digital system replacing SRTS's manual, clipboard-driven audit process. I led the technical implementation of the report generation deliverable — building and deploying the web application end-to-end, including the ArcGIS REST API integration, LLM prompting pipeline, and .docx report templating system.

Demo.

The Problem.

The walkability audit process had three interconnected pain points that limited SRTS's reach and advocacy capacity:

1. Duplicate data entry. Audit participants documented observations on physical clipboards during site walks. After each visit, Harriet manually transcribed all handwritten notes into a Google Doc — recording every observation twice, often days later when handwriting was hard to read.

2. Manual report compilation. When city council or DOMI teams requested audit findings to evaluate infrastructure funding, Harriet had to manually compile scattered notes into coherent stakeholder reports. A process taking multiple days meant SRTS couldn't respond quickly when decisions were being made.

3. Inaccessible historical data. Past audit data was scattered across Google Docs, email threads, and physical storage boxes with no consistent structure. Harriet couldn't easily answer: which schools have the most persistent safety concerns? Are conditions improving after infrastructure investments?

Deliverable 1 — ArcGIS Survey123 Forms.

Post-Survey Form →    Pre-Survey Form →

Replaces paper clipboards with a structured two-part digital workflow built on ArcGIS Survey123, using Harriet's existing DOMI license — eliminating new software costs and IT dependencies.

The pre-survey is sent to school staff before the audit walk. It captures student transportation patterns, known safety concerns along common walking routes, and school-specific context — so the audit team arrives already informed.

The post-survey is completed by audit participants after the walk, with role-specific question branching across five participant types: SRTS Coordinator, City Planner, Traffic Engineer, PPS Transportation, and School Staff. Each participant sees only the questions relevant to their role, reducing cognitive load and improving data completeness.

A controlled dropdown of 46 Pittsburgh public elementary and middle schools (pulled from a live ArcGIS hosted feature layer) enforces consistent naming across every submission — the foundational requirement for any future cross-audit analysis.

Before vs. After — Data Collection.

Before After
Physical clipboards & printed checklists during site walks Digital Survey123 forms completed on participants' phones after the walk
Harriet manually transcribed handwritten notes into Google Docs Responses automatically stored in ArcGIS hosted feature layers — immediately accessible
Single form for all roles — inconsistent, incomplete data Role-specific branching across 5 participant types — everyone sees only relevant questions
No controlled vocabulary — school names entered inconsistently Controlled dropdown of 46 Pittsburgh public schools enforces consistent naming

Deliverable 2 — Report Generation Web App.

Live App →    GitHub Repo →

A deployed web application that pulls audit responses from ArcGIS via the ArcGIS REST API, passes structured multi-role data to Claude (Anthropic LLM) for synthesis, and generates three audience-specific audit reports as downloadable .docx files — all in under 5 minutes. This replaces a multi-day manual compilation process.

Three report formats generated from the same underlying data:

DOMI Internal — Technical findings organized by role (Planner, Traffic), infrastructure severity ratings, priority concern summary, and recommended actions tiered by urgency.

School & Community Partner — Accessible summary of route conditions, transportation data, key findings, and next steps — designed for school administrators and parents.

General Public — One-page community update with program context, key statistics, and high-level findings for broad distribution.

Reports download as editable Word documents so Harriet retains full editorial control. The LLM output is a structured first draft — she remains the authoritative voice on every report that leaves her office.

Before vs. After — Report Generation.

Before After
Manual compilation of audit notes into reports — multiple days per audit Reports generated in under 5 minutes from a single browser interface
Single generic format manually reformatted for each stakeholder group 3 audience-specific formats generated automatically: DOMI Internal, School & Community, General Public
No standard schema — comparison across audits was impractical Consistent structured schema enables over-time comparison across every audit

Pilot Results.

The full system was tested at a live walkability audit at Pittsburgh Morrow Elementary on March 26, 2026 — with real city planners, traffic engineers, the SRTS coordinator, PPS transportation staff, and school representatives.

7 of 7 participants submitted responses digitally with no prior training on the system. 0 paper forms were collected. Real pilot data was subsequently used to generate the first set of reports through the web app, which were reviewed and approved by Harriet Jackson across all three formats.

The system is fully handed off and runs independently within Harriet's existing DOMI ArcGIS Online account. No new software licenses were required. Ongoing cost: under $0.05 per report generation in Claude API usage, hosted on Vercel's free tier.

Technology Stack.

Data Collection: ArcGIS Survey123 · ArcGIS hosted feature layers · srts_schools controlled vocabulary layer (46 schools)

Report Generation: ArcGIS REST API (data pull) · Claude / Anthropic API (LLM synthesis) · python-docx (.docx generation) · Vercel (deployment)

My Role: Built and deployed the report generation web application end-to-end — ArcGIS REST API integration, LLM prompting pipeline, three .docx report templates, and a developer tools page (/dev) for DOMI IT to verify credentials and inspect the data pipeline independently.
